# BRD — DX 전환을 위한 조직·구성원 데이터 표준화 및 품질 진단

> - 상태: 초안 (v0.3)
> - 작성일: 2026-08-25
> - 프로젝트 기간: 2026-08-27 ~ 2026-08-28

## 1. Project Overview

### 1.1 문서 목적

이 문서는 레거시 조직·구성원 데이터를 표준화하고 데이터 표준 사전을 구축하는 프로젝트의 공통 실행 기준을 정의한다. 프로젝트의 사업 목적, 기준 데이터, Bronze·Silver 레이어의 책임, 데이터 품질 기준, Accepted·Rejected 결과 제공 방식, 산출물 및 완료 조건을 명시한다.

> 구현 방법과 세부 처리 규칙은 PRD 및 기술 설계 문서에서 정의한다.

### 1.2 프로젝트 목적

1. DX 전환을 준비하는 기업의 레거시 조직·구성원 데이터에 일관된 표준과 품질 규칙을 적용하여 활용 가능한 데이터로 전환한다.
2. 표준화 및 품질 검증 과정에서 확인된 데이터 이슈를 필드·레코드·실행 회차 단위로 분류하고 추적 가능한 형태로 제공한다.
3. 기업이 현재 데이터의 활용 가능 범위와 후속 개선 대상을 객관적으로 판단할 수 있도록 지원한다.

### 1.3 제공 가치

- 표준화 가능한 데이터는 합의된 구조·타입·코드와 관계를 갖는 Accepted 데이터로 제공한다.
- 판단하거나 변환할 수 없는 데이터는 임의로 보정하지 않고 원본값·대상 필드·실패 규칙·사유와 함께 Rejected 데이터로 제공한다.
- Accepted 및 Rejected 비율과 품질 이슈 분포를 통해 DX 전환 이전의 데이터 준비 상태를 보여준다.
- 원천부터 Accepted·Rejected 결과까지 데이터 계보를 추적하여 결과의 재현성과 검증 가능성을 확보한다.

### 1.4 최종 산출물

1. 기준 데이터 인벤토리 및 AS-IS 데이터 프로파일링 결과
2. 회차별 원천 데이터, Bronze 매니페스트 및 수집·실행 이력
3. 데이터 표준 사전, Legacy→표준명 매핑, 허용값 및 변환·검증 규칙
4. Bronze·Silver TO-BE 모델, 엔터티 관계 다이어그램(ERD) 및 데이터 계보
5. Accepted 표준 데이터와 정규화된 RDB 테이블
6. Rejected 레코드와 필드 단위 품질 이슈가 저장된 MongoDB 컬렉션
7. 수집·표준화·검증·분류·적재 파이프라인과 자동 검증 결과
8. Accepted 데이터와 Rejected 품질 이슈를 조회하는 Django 기반 화면

### 1.5 주요 사용자 및 이해관계자

- DX 전환 담당자
- 데이터·IT 운영 담당자
- 조직·인사 데이터 담당자
- 표준화 결과와 데이터 품질 상태를 검토하는 내부 사용자

### 1.6 핵심 사업 가치

본 프로젝트는 원천 데이터의 사실 여부를 임의로 보정하거나 완전성을 보장하는 것이 아니다. 일관된 기준으로 처리 가능한 데이터와 별도의 확인·개선이 필요한 데이터를 명확히 구분하고, Accepted 데이터와 Rejected 품질 이슈를 함께 제공한다. 이를 통해 기업은 DX 전환에 활용할 수 있는 데이터 범위와 후속 개선 대상을 객관적으로 파악할 수 있다.

## 2. Business Background & Data Baseline

### 2.1 배경

DX 전환을 추진하는 기업은 기존 조직·구성원 데이터를 새로운 시스템 또는 분석 환경에 활용해야 한다. 그러나 레거시 데이터에는 동일한 업무 개념이 서로 다른 식별자·상태값·날짜·명칭으로 표현되거나 조직과 구성원 정보가 하나의 구조에 혼재되는 문제가 존재한다.

본 프로젝트는 공식 기준 데이터를 이용해 표준 사전과 품질 기준을 확정하고, 프로젝트 수행 기간 동안 합의된 웹 페이지에서 3분 간격으로 데이터를 반복 수집한다. 수집된 데이터에는 최초 확정된 정제·표준화·검증 규칙을 매 실행 회차 동일하게 적용한다.

### 2.2 공식 기준 데이터

공식 평가 기준선은 CSV 4종, 총 104,000행, 파일 기준 총 24개 컬럼이며 중복을 제거하면 16개 고유 필드이다.

| 원천 파일 | 데이터 행 수 | 컬럼 수 | 주요 역할 |
| --- | ---: | ---: | --- |
| `biz_employee_master.csv` | 3,000 | 6 | 직원 마스터 |
| `biz_meta_area_50000.csv` | 50,000 | 5 | 업무 영역 마스터 |
| `biz_meta_area_join_ready.csv` | 50,000 | 9 | 직원·상위 영역 정보가 결합된 대조용 데이터 |
| `biz_meta_area_parent_lookup.csv` | 1,000 | 4 | 최상위 영역 조회 데이터 |
| **합계** | **104,000** | **24** | 파일별 컬럼 수 합계 |

주요 관계 후보는 다음과 같다.

- `MANAGER_EMP_NO → EMP_NO`: 영역 관리자와 직원 마스터의 참조 관계
- `PARENT_AREA_ID → AREA_ID`: 하위 영역과 상위 영역의 계층 관계
- `biz_meta_area_join_ready.csv`: 표준 변환 및 조인 결과를 검증하는 대조 데이터

`biz_legacy_integrated.csv`는 공식 4종·104,000행 기준선에 포함하지 않고 별도 레거시 입력 또는 확장 검증 데이터로 관리한다. 공식 범위에 포함하려면 데이터 인벤토리, 기준 행 수, 표준 사전 및 품질 규칙을 함께 갱신해야 한다.

### 2.3 반복 수집 데이터 계약

크롤링 데이터의 컬럼 구조와 형식은 사전에 제공된 `sample_data.csv`와 동일하다. 프로젝트 기간인 약 이틀 동안 내부망의 `http://192.168.0.51:8000/`에서 API 키 인증을 사용하여 3분 간격으로 수집하며, 각 실행 결과는 원본값을 보존한 회차별 Raw 데이터로 저장한다. 공식 CSV 기준선은 표준과 평가 기준으로 유지하고, 크롤링은 동일한 Bronze 입력 원칙을 따르는 반복 수집 채널로 사용한다.

### 2.4 문제 정의

| 문제 | 확인된 예시 | 비즈니스 영향 |
| --- | --- | --- |
| 식별자 표기 불일치 | `BIZ_00170`, `BIZ-00788`, `BIZ 17549`, 대소문자 혼용 | 동일 개체를 중복 또는 서로 다른 개체로 인식할 수 있음 |
| 속성값 표준 부재 | `재직`, `사용`, `YES`, `Y`, `1`, `0`, `퇴직` | 재직 상태와 활성 여부를 일관되게 해석할 수 없음 |
| 계층 표현 혼재 | `TOP_LEVEL`, `TOP LEVEL`, `최상위`, `L1`, 빈 값 | 조직 계층과 분석 기준이 불명확함 |
| 날짜 형식 불일치·결측 | ISO, 슬래시, 점, 숫자형 일시 및 빈 값 | 날짜 기반 검증과 활용이 어려움 |
| 조직·사람 정보의 혼재 | 조직 정보와 관리자·구성원 정보가 동일 구조에 존재 | 데이터 변경·중복·관계 관리가 어려움 |
| 품질 문제의 가시성 부족 | 실패 필드, 원본값, 실패 규칙과 사유가 별도로 관리되지 않음 | DX 전환 전 확인하거나 개선해야 할 대상을 파악하기 어려움 |
| 임의 보정 위험 | 판단 근거가 없는 값을 정상값으로 변환 | 잘못된 데이터가 정상 데이터로 확정될 수 있음 |
| 실행·계보 추적 부족 | 수집 회차, 입력·코드 버전, 처리 상태와 출력 위치가 기록되지 않음 | 결과를 재현하거나 원천까지 역추적하기 어려움 |

`biz_meta_area_parent_lookup.csv`의 `REG_DT` 값 차이처럼 기준 소스와 시점을 확정할 수 없는 경우 임의로 한쪽 값을 선택하지 않는다. 기준 소스·기준 시점 규칙을 먼저 문서화한 후 변환하며, 판단이 완료되지 않으면 Rejected 품질 이슈로 분류한다.

## 3. Target Data Architecture

### 3.1 Medallion 아키텍처

```text
공식 CSV / 웹 크롤링 원천
            ↓
Bronze — 원본 + 수집 메타데이터 + 실행 매니페스트
            ↓
Silver — 표준명 + 표준 타입 + 품질 검증
            ↓
     ┌───────────────────┬────────────────────┐
     │ Accepted          │ Rejected           │
     │ 표준·정규화 데이터│ 실패 레코드·이슈   		   │
     │ RDB 적재          │ MongoDB 적재         │
     └───────────────────┴────────────────────┘
            ↓
Django 기반 표준 데이터·품질 이슈 조회
```

Medallion 레이어는 데이터 처리 책임과 계보를 구분하는 논리·물리 구조로 사용한다. RDB와 MongoDB는 애플리케이션 조회를 위한 결과 저장소로 사용한다.

### 3.2 Bronze — 원본 및 수집 사실 보존

Bronze는 프로젝트 기간 동안 원본과 수집 사실을 재현 가능하게 보존하는 영역이다. 업무 규칙에 따른 수정이나 표준화는 수행하지 않는다.

Bronze에는 다음 정보가 포함되어야 한다.

- 수집 당시의 원본 파일 또는 원문 응답
- `run_id`, 원천 식별자·URL, 수집 시각, 파일명과 콘텐츠 유형
- 입력 버전, 크롤러·처리 코드 버전, 실행 상태와 출력 위치
- 파일 크기 및 SHA-256 체크섬
- 성공·부분 실패·실패 여부와 실패 사유

원천 컬럼명, 값, 공백, 대소문자와 오류 형태를 그대로 보존하며 실행 회차별로 구분한다. 파싱할 수 없는 원본도 정상 데이터와 분리하고 실패 사유를 기록한다.

### 3.3 Silver — 표준화·검증·분류

Silver는 Bronze 원본에 표준 사전과 품질 규칙을 적용하는 영역이다. 컬럼명, 타입, 식별자, 상태값, 날짜와 문자열 표현을 일관되게 만들고 각 레코드를 Accepted 또는 Rejected로 판정한다.

주요 처리는 다음과 같다.

- 16개 고유 필드의 Legacy→표준명 매핑과 타입 적용
- 식별자 대소문자, 앞뒤·전각 공백, 날짜 및 논리값 표현 통일
- 필수값, PK 후보 중복, FK 참조, 허용 도메인과 조인 결과 검증
- Accepted 데이터와 Rejected 레코드·필드 이슈 분리
- 원본값, 대상 필드, 검증 규칙, 실패 유형과 사유 기록

Accepted Silver 데이터는 승인된 제외·격리 규칙을 반영한 후 PK 후보 중복, 필수값 결측, FK orphan, 도메인 위반, 조인 대조 불일치 및 타입 변환 실패가 없어야 한다. 기준을 충족하지 못한 데이터는 억지로 통과시키지 않고 Rejected로 격리한다.

### 3.4 공통 설계 원칙

- Bronze 원본 보존과 Silver 표준화·검증의 책임을 섞지 않는다.
- 모든 실행은 `run_id`, 처리 시각, 입력 버전, 코드 버전, 출력 위치와 검증 결과를 추적할 수 있어야 한다.
- 같은 입력과 같은 규칙·코드 버전으로 재실행하면 같은 결과가 나와야 한다.
- 실패 데이터는 정상 데이터와 섞지 않고 격리하며 실패 원인과 처리 상태를 기록한다.
- 원천 실행부터 Bronze·Silver와 최종 저장소까지 역추적할 수 있어야 한다.

## 4. Business Objectives & Success Metrics

### 4.1 사업 목표

1. 기업의 조직·구성원 데이터를 동일한 표준과 품질 기준으로 반복 처리한다.
2. 활용 가능한 Accepted 데이터와 개선이 필요한 Rejected 데이터 및 품질 이슈를 명확히 분리한다.
3. Accepted 데이터로 DX·분석 활용 목적의 표준 모델을 제공한다.
4. Rejected 데이터의 대상 필드·원본값·실패 규칙·사유를 제공하여 후속 개선 범위를 판단할 수 있게 한다.
5. 표준 데이터와 데이터 품질 이슈를 조회할 수 있도록 한다.

### 4.2 데이터 및 처리 상태 정의

- Raw/Bronze 데이터: 원천값을 변경하지 않고 실행 회차와 수집 메타데이터를 함께 보존한 데이터
- Accepted 레코드: 필수값·형식·허용값·참조 관계 등의 Silver 품질 검증을 통과한 레코드
- Rejected 레코드: 핵심 필드 누락, 매핑 불가, 동일 회차 내 비정상 중복 등으로 표준 데이터로 확정할 수 없는 레코드
- 데이터 품질 이슈: 원본 레코드와 필드, 원본값, 검증 규칙, 실패 유형과 사유를 기록한 정보
- 실행 회차: 수집부터 Bronze 저장, Silver 변환·검증·분류 및 저장소 반영까지의 처리 단위

서로 다른 실행 회차에서 동일 개체가 반복 관측된 경우는 그 자체로 Rejected 중복으로 보지 않는다.

### 4.3 성공 지표

Accepted 비율과 Rejected 비율은 원천 품질에 따라 달라지므로 프로젝트 성공 목표가 아니라 진단 결과로 보고한다.

| 지표 | 측정 방법 | 목표 |
| --- | --- | ---: |
| 기준 데이터 재현율 | 공식 CSV 4종의 파일·행 수 기준선과 Bronze 적재 결과의 일치 비율 | 100% |
| 실행 매니페스트 완전성 | 필수 실행·수집 메타데이터가 기록된 실행 회차의 비율 | 100% |
| 데이터 처리 판정률 | 전체 Silver 입력 레코드 중 Accepted 또는 Rejected로 판정된 비율 | 100% |

- `biz_legacy_integrated.csv`의 별도 레거시·확장 검증 입력 관리

- 회차별 원본, 실행 매니페스트 및 체크섬을 포함한 Bronze 구성
- 16개 고유 필드 중심의 AI 데이터 표준 사전과 매핑 규칙 정의
- 확정된 정제·표준화·검증 규칙의 반복 적용
- Silver Accepted·Rejected 판정과 필드 단위 품질 이슈 생성
- Accepted 데이터의 정규화 및 RDB 적재
- Rejected 데이터와 품질 이슈의 MongoDB 적재
- 실행·품질 로그, 데이터 계보 및 자동 검증 결과 제공
- Django 기반 표준 데이터·품질 이슈 조회 화면 제공

- 근거가 불충분한 값의 임의 보정 또는 원천 데이터의 업무적 사실성 보증
- 프로젝트 기간 중 원천 스키마 변경을 자동 감지하여 표준화 규칙을 재설계하는 기능
- 프로젝트 종료 후 데이터 보관, 정기 크롤링 및 파이프라인 상시 운영

## 7. Constraints / Assumptions / Dependencies

### 7.1 제약사항

- 웹 수집은 대상 페이지의 이용 조건, 접근 정책, 인증 범위와 호출 제한을 준수해야 한다.
- 반복 수집은 프로젝트 기간 동안 3분 간격으로 수행하며 네트워크와 실행 환경에 따라 계획 시점과 실제 수집 시점에 차이가 발생할 수 있다.
- 웹 페이지 구조 변경, 접속 오류 또는 접근 제한으로 일부 실행 회차가 실패할 수 있다.
- Medallion은 Bronze·Silver의 책임을 구분하는 논리적 레이어로 적용한다. 현재 Bronze 원본은 회차별 Raw CSV로 저장하며, 서비스 저장소는 Accepted RDB와 Rejected·품질 이슈 MongoDB로 분리한다.
- RDB와 MongoDB는 프로젝트 착수 시점의 최신 안정 버전을 사용한다.
- 애플리케이션 및 조회 화면은 Django를 사용한다.
- 수집·가공 데이터는 프로젝트 내부 검증 및 시연 목적으로만 사용한다.

### 7.2 가정

- 크롤링 데이터는 `sample_data.csv`와 동일한 컬럼 구조와 데이터 형식을 유지한다.
- 정제·표준화·검증 규칙은 최초 합의 후 변경되지 않으며 모든 실행 회차에 동일하게 적용한다.
- 프로젝트 기간 동안 수집 대상 웹 페이지의 구조와 접근 조건이 크게 변경되지 않는다.
- 수집 대상 페이지와 데이터 항목은 착수 시 합의하며 실행 주기는 3분으로 고정한다.
- 수집 대상 데이터는 실제 개인을 식별하기 위한 개인정보가 아닌 프로젝트용 데이터이다.
- 원천 데이터의 업무적 의미가 잘못되었거나 판단 근거가 없는 경우 이를 임의로 수정하지 않는다.

### 7.3 의존성

- 공식 CSV 4종과 추가 레거시 파일의 제공 및 기준 범위 확인
- 수집 대상 URL, 접근 가능 여부와 데이터 수집 범위 확정
- 데이터 표준, 허용값, 관계, 변환·검증 규칙에 대한 합의
- 반복 파이프라인을 실행할 수 있는 네트워크 및 실행 환경
- Django, 최신 안정 버전의 RDB 및 MongoDB 저장·실행 환경
